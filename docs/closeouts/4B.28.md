THE ROUND TRIP IS EXACT. Thaw 8, re-freeze 8, absorb 8, and the placements are
byte-identical to the board we started on. That is R-F1(b) as a property and not
as a comment: a thaw changes AUTHORITY, never POSITION, which is why the module
contains no solver at all.

WHAT THAT BUYS ARCHITECTURALLY. The child shares its parent's RUN and SNAPSHOT,
because the placements ARE the parent's placements. No snapshot copy, no
re-extraction, no re-solve -- and, the part that matters, the ask path keeps
working unchanged, because it reads the same evidence in the same run dir.

  ceremony wall: preview + apply, sub-second on a 386-bar board.

THE GRIP HAD TO BECOME PERSISTENT, AND THE HARNESS IS WHAT FOUND IT. Every
marker in the overlay is torn down and rebuilt on each redraw, which is fine for
a line nobody touches. The grip is a POINTER TARGET, and redraw fires on every
pan, zoom and vis `changed` event -- so a rebuilt grip can be replaced between
the moment a pointer is aimed at it and the moment the button goes down, and the
press lands on a detached node. In isolation the spec was 44/44; under the full
ladder, with other specs having warmed the page, two boundary tests failed
intermittently. The frozen marker and its grip are now built ONCE and only
REPOSITIONED, with the listeners bound once. It would have cost a planner a
boundary drag that sometimes does nothing -- and "sometimes does nothing" is the
hardest kind of defect to report.

THE ASK PATH NEEDED ONE PARSE WIDENING, AND THE MEASUREMENT FOUND IT. On the
first live run "why is ORD-000001 pinned?" went to `attribute-lookup`, which
correctly reported it could not find that field -- because "pinned" is not a
declared field. It is a fact about AUTHORITY. The same order asked as "is
ORD-000001 in the frozen zone?" got the whole answer. `frozen`'s MEANING now
owns "pinned" / "held" / "why can't the solver move this one" and says out loud
that pinned is not a field. Parse prompt v15 -> v16. NO new intent: the route
existed and the assembler could already answer -- 4B.27's rule for the third

3. WHAT ELSE SHIPPED
================================================================================

ITEM 2 -- SCREEN ROOM

  (a) THREE COLLAPSIBLE DOCKS. Tray, coarse look-ahead and ask panel each
      collapse to a labelled edge with a LIVE BADGE, persisted per browser.
      Defaults per the brief: tray and coarse COLLAPSED, ask OPEN.

      THE BADGE SURVIVES THE COLLAPSE, and that is the whole design. A collapsed
      tray reading "BEYOND THE HORIZON  122" is not a hidden tray -- known work
      stays visible somewhere, which is the Glass Box cardinal danger the tray
      exists to answer. Collapsed means "not expanded", never "not there".

  (b) DOWNTIME COMPRESSION.  MECHANISM CHOSEN: vis-timeline's own `hiddenDates`,
      NOT a custom scale, AND THE DROP MAPPING IS WHAT DECIDED IT. Every
      pixel<->instant conversion in this cockpit goes through
      `timeline.body.util.toScreen/.toTime` (geometry.js is the one place that
      reads vis's layout), and vis applies hidden ranges INSIDE those two
      functions -- so R-DP9's tolerance arithmetic, 4B.23's time mapping and the
      drag's pin stay exact under compression with no second coordinate system
      to keep in step. A custom scale meant re-deriving that mapping by hand, and
      a drop landing minutes off is worse than an uncompressed board.

      Only spans where EVERY row is closed are folded: hidden dates are a
      property of the AXIS, not a row, so compressing a span one machine works
      through would hide real work.

      FOLD MARKS ARE NOT DECORATION. A hidden range has ZERO width, so without a
      mark two bars either side of a folded night render as TOUCHING -- and
      "these two jobs are back to back" is a claim about the plant that
      compression would be inventing. Every seam carries a hatched tear, a notch
      on the ruler, and a tooltip that says "the bars either side are NOT
      adjacent".

      TOGGLE, persisted, LINEAR BY DEFAULT: verifying a calendar claim is
      unanswerable on a folded ruler, and nobody's ruler gets folded unasked.

      GUARD, green: a REAL drop at a KNOWN instant with the ruler folded, the
      pin asserted against the request payload -- exact to the minute.

  (c) VERTICAL DENSITY as tokens (`--lane-min-h`, `--lane-pad-y`, `--bar-h`,
      `--bar-label-fs`). Defaults deliberately conservative: pushed further the
      bar label clips, and a bar whose order number cannot be read is a bar a
      planner cannot act on. Knobs for the panel pass, not a finished answer.

ITEM 3 -- THE JOB PANEL

  Click a bar, see the WHOLE JOB: every operation of the order with its sequence,
  machine, start/finish, working time, chunk count, disposition chips
  (committed / pinned / N pieces) and the board's own lateness badge. The clicked
  operation is marked; clicking another row scrolls the board to it, flashes it
  and moves the selection. Tray entries for the same order appear with their
  disposition and due date, so a part-placed order reads as one job.

  EVERY QUANTITY COMES FROM THE BOARD'S OWN DERIVATION (`jobRowsForOrder` is
  `jobFor`, the same function the hover card reads). Nothing in the panel
  computes a duration, a band or a disposition. Five of the last six category
  fusions in this product were a name written once, by whoever needed a number,
  and never re-read as a claim; a panel that recomputed working time would be the
  sixth.

  WORKING TIME AND SPAN are named separately and shown together ONLY where they
  differ -- on an unchunked operation they are the same number, and printing both
  invites a planner to look for a difference that is not there (4B.20).

  THE TWO INTENT BUTTONS CARRY THE OPERATION, which INCIDENTALLY DISCHARGES
  4B.30 section 5a.118(c) FOR BOARD USERS: `op_seq` is unparseable in text, so
  every multi-op order's typed question answers about its FIRST operation. A
  panel row click carries it exactly, with no parse in the way. Asserted on the
  wire.

  ONE THING HAD TO CHANGE UNDERNEATH: `board.onSelect` held a SINGLE callback and
  overwrote it. The job panel subscribing would have silently unsubscribed the
  ask panel's deictic scope -- "why is this one late?" losing its subject with
  nothing on screen to say so. It is a subscriber list now.

ITEM 4 -- THE GESTURAL DEBT

  (a) THE CHUNKED DRAG. Built: dragging any piece drags the OPERATION, the pieces
      travel as one (one carry ghost per chunk, rigidly offset), and the board
      does not pan. ON DROP IT DECLINES VISIBLY, in the ask path's own words.

      THE DECLINE WAS THE RIGHT CALL, not a shortcut. 4B.30 ruled the ask path
      declines a chunked move because its pauses are placements the solver made
      around calendar closures and a local shift cannot re-derive them. Pricing
      it on the board would have made two surfaces state two different limits.

      SO THE ASK PATH'S OWN COPY WAS CORRECTED IN THE SAME COMMIT. It ended
      "Dragging the bar on the board runs the full re-solve, which can." It does
      not, and it never has -- the board's drag was inert on a chunked bar. It
      now reads "Dragging the bar on the board declines for the same reason -- it
      is one limit, not two surfaces disagreeing." ONE LIMIT, SAID THE SAME WAY
      ON BOTH SURFACES. 4B.30 section 5a.118(h) DISCHARGED.

      A DECLINE IS A THIRD REGISTER and gets its own card class: not the rejected
      red of a proven-impossible placement (a claim about the plant) and not the
      alarm of a failure (something that broke). It offers NO "try again" -- that
      button would promise a different answer to the identical gesture. Checked
      from the ROW before any request, so it costs no model build.

      ROOT CAUSE, for the record: `onPointerDown` tested the item id against the
      ASSIGNMENT index, and after 4B.20 a chunked bar's items are PIECES
      (`<id>~c0`, `~c1`). A piece id is not an assignment id, so the gesture
      never started and vis's own Hammer pan took the drag.

  (b) THE R-DP9 TOLERANCE. It read `grid_px * pxToMinutes(1)` -- 8 PIXELS
      expressed in minutes, about 240 minutes at the default 30-day view. A
      deliberate four-hour drag was classified "already here" and priced nothing;
      4B.23 lost three verification gestures to it.

      THE TOLERANCE IS FOR CLICK JITTER, NOT FOR INTENT. Jitter is a property of
      the hand; it does not get larger because the board is zoomed out. It is now
      a FIXED constant in WORKING MINUTES (`feel.snap.noop_tol_min` = 5) and the
      zoom cannot touch it.

      AND A NO-OP SAYS SO: "that's where it already sits -- within 5 minutes of
      its current start, so there is nothing to price". It stays a TIP and not a
      card, because R-DP9 rules this calmer than a refusal. 4B.23 made "nothing
      reverts in silence" the law for failures; it now covers no-ops.

  (c) THE STALE-SELECTION HAZARD. Verified by driving it: select one bar, drag a
      different one, assert the pin on the wire names the DRAGGED bar. Green.
      4B.23/24 did already guarantee it; the test was cheap and is now standing.

  ONE DEFECT FOUND ON THE WAY, NOT IN THE BRIEF. `board.rebind` predated 4B.20's
  per-chunk rendering: it called `items.update({id: assignment_id, ...})` against
  an id that is not an item on a chunked bar, and vis-data INSERTS on update. So
  every accepted edit on a board with any split operation raised a PHANTOM MERGED
  BAR spanning the pauses, on top of the pieces still there. The build and the
  rebuild are one builder and one remover now, and removal is by PREFIX because a
  re-solve can re-chunk.

6. WHAT WAS TEMPTING AND LEFT
================================================================================

PRICING THE CHUNKED DRAG. The machinery is nearly there -- `apply_pin` binds a
start and the model re-derives the chunks. It was tempting and it was wrong: the
ask path RULED in 4B.30 that a split operation cannot be locally priced, and a
board that priced it would have made two surfaces state two different limits
about one operation. The brief allowed either; the decline is the one that leaves
the product coherent. If it is ever priced, it must be priced on BOTH surfaces in
the same commit.

MAKING THE THAW RE-SOLVE. A thaw hands placements to the planner, and it is
tempting to then ask the solver what it would do with the freedom. That is a
DIFFERENT RULING from the one R-F1 made. Authority changed; position did not; the
guard asserts it as a property.

A GENERAL `unpin`. The freeze absorbs pins, which is a release -- and it would
have been one small step to a general release verb. Kept deliberately narrow:
this releases ONLY pins the frozen front now binds anyway, so no placement is
ever left unheld. `unpin` stays a named carry-forward.

WIDENING THE PARSE FURTHER. "pinned" reaches `frozen` now. "held", "locked",
"why won't it move" were all tempting to add as separate meanings; one widened
meaning covers them, and a vocabulary-class change buys nothing where the route
already answers.

FIXING THE `deictic` RED. It is red at HEAD, it is named, and a cockpit session
fixing an ask-path regression it did not cause is how sessions lose their scope.

CLAUDE.md COMPRESSION. Out of scope by the brief, and now ~105k against a 40k
ceiling. It remains the largest single item owed at the next phase exit.

7. NOT FIXED -- REPORTED, DELIBERATELY
================================================================================

(a) STANDING PINS DO NOT SURVIVE A SLICE ROLL. Splicing seam 3 is unbuilt. The
    thaw gesture now mints exactly the objects seam 3 must learn to preserve --
    which makes this the strongest argument yet for seam 3 being NEXT after the
    demo. Said in docs/07 where the roadmap reads it.

(b) THE COMPRESSION GUARD PROVES INVARIANCE, NOT THE DEMO-BOARD MAGNITUDE. The
    rolling fixture spans ~5 days, so its default view cannot reproduce the
    240-minute swallow the 30-day demo board produced. The tolerance control
    fired at 155.5 vs 175.0 minutes -- real, and smaller than the live defect.
    The property (the tolerance does not scale with zoom) is what is guarded.

(c) THE FOLD SET IS PLANT-WIDE, NOT PER ROW. Only spans where EVERY machine is
    closed are folded. That is the only honest choice given hidden dates are an
    axis property, and on this plant it is the nights and weekends. On a plant
    with staggered shifts it will fold much less, and the feature will quietly
    do less than it appears to promise. Nothing on screen says so.

(d) THE BOUNDARY DRAG SNAPS TO THE HOUR, and the snap is a token nobody has
    tuned against a real planner. An hour is defensible on a board whose frozen
    days are whole days; it is an authored guess.

(e) THE CONFIRMATION BEAT DOES NOT NAME THE ORDERS. It states the count and the
    direction, which is what R-F1(e) asks for. On a thaw of 40 it would be more
    useful to list a few -- the plan carries `changed` with work orders in it and
    the card simply does not read them.

(f) A BOUNDARY MOVE ON A MONOLITHIC BOARD IS UNTESTED IN THE BROWSER beyond "the
    handle is not offered". The refusal is guarded in Python. 4B.30
    section 5a.118(g)'s shape.

(g) THE JOB PANEL'S TRAY BRANCH IS UNEXERCISED LIVE. `_derive_maps` keeps ONE
    work package per demand, so a part-placed order is not currently producible
    (4B.22 B3). The branch is written and correct against the data shape; no
    board this session could show it.

(h) THE ASK PATH STILL CANNOT BE ASKED "WHY IS THIS BAR PINNED" WITHOUT NAMING AN
    ORDER. "why is this bar held?" with no subject lands on CLARIFY `no-subject`,
    honestly. The BOARD SELECTION resolves it; a bare deictic does not.
    Section 5a.79's ladder, unchanged.

(i) `--calibrated` IS A FLAG ON A SPIKE SCRIPT, not a product path. Minting a
    board under its plant's accepted profile should not require knowing that
    naming K refuses the profile. The trap is documented in the file and is
    still a trap.
