visible there because somebody was writing prose about it. Every seam that got it
wrong is a DATA surface -- a document field, a row dict, a tool payload -- where
the field name is written once, by whoever needed a number, and never read again
as a claim. `duration_minutes` was not a lie anybody told; it was a name nobody
re-read.

IDENTICAL EVERYWHERE. The reason is exact: on this board both chunked operations'
pauses fall WHOLLY inside a closure --

  ORD-000011 op10  CUT-01  pieces=3  span=5821  work=1501  open_inside_span=1501

time because there is no open time inside the pause to over-count.

SO THE BOARD WAS RIGHT, AND RIGHT BY A PROPERTY OF THE DATA THAT NOTHING

preemption -- would have inflated the strip and hidden real idle capacity from
the bands. 4B.13 recorded this seam as "already correct"; it was correct, and it
was not safe. It is now per-chunk, right by construction, and the change is
provably a no-op on this board.

ITEM 3 -- THE GUARD
======================================================================

tests/test_working_time_vs_span.py, 19 tests. TWO MECHANISMS, because neither
alone closes the class:

  (1) THE NAMING REGISTER. Every tool is CALLED, and every numeric field in every
      row and summary whose key looks like a time quantity must appear in an
      authored register declaring which quantity it carries (WORKING / ELAPSED /
      CAPACITY / NEITHER). Fields are discovered by calling, not by reading
      source, so a new field cannot be added where the test does not look. This
      is the class-level half.

  (2) THE VALUE PROPERTY. Registering a field as WORKING does not make it working
      time. Every WORKING field must equal the sum of the run windows, and no
      duration attributed to work may exceed the resource's open capacity over
      the same interval -- the 3.9x tell that found the defect.

ITS LIMIT, STATED IN THE MODULE DOCSTRING (the standard 4B.19's phrase-list guard
set): it is scoped to the SYNTHESIS TOOLBOX row and summary surface. A
span-as-duration in a renderer, in a route's key facts, in the schedule document,
or in the cockpit's JavaScript is INVISIBLE to it. "A fifth seam is impossible"
is not the claim; "the surface where the class was last found, and where new
tools are most likely to be added, is now watched" is. The two known-correct
sites it does not watch are named in the docstring by name.

THE PREMISE TEST runs first and asserts the fixture contains a genuinely chunked
operation whose span exceeds its work AND whose pause falls inside a closure --
without the second half, the capacity property could be satisfied by coincidence.
Specimen: the pinned world's own ORD-000011 op10, transcribed as plain data on
test_attribute_lookup's discipline.

ITEM 5 -- WHAT THE FIX BROKE, AND WHY IT IS THE SESSION'S SECOND RESULT
======================================================================

MAKING THE ANSWER TRUER MADE IT UNVERIFIABLE.

With the toolbox fixed but before this was found, the second tier drafted, on the
pinned world:

    "ORD-000011 op10 runs on CUT-01 from 2026-01-08 14:36 to 2026-01-12 15:37,
     and puts 1501 minutes of actual work on the machine."
    "The elapsed span from start to end is 5821 minutes, but this includes 4320
     minutes of pause, since the operation is split across 3 pieces."

with four real record ids cited. VERIFICATION CUT ALL THREE CLAIMS. The rendered
answer was "I couldn't answer that one from the evidence."

MECHANISM. claim_verifier re-fetches a claim's cited records and checks its
figures against them. `working_minutes` is a SUM OVER RUN WINDOWS and lives in no
single record, so the re-fetch cannot rebuild it. This never bit before because
the only row duration WAS end - start, which the verifier could reconstruct from
the two timestamps the records do contain. Reporting working time made the figure
unreconstructable.

Summary figures were already trusted for exactly this reason -- the code comment
says "they are our own arithmetic over the pinned run". Derived ROW figures now
are too, through a NAMED SET (`_DERIVED_ROW_FIGURES`) rather than "every number in
a row": a value copied verbatim from a record must still be found in that record,
or the re-fetch stops being a check. Two tests pin it, one of which goes red if
the trusted set is widened.

THE LESSON OUTLIVES THIS DEFECT: a session that only checked the NUMBER would
have shipped a regression from a false confident answer to a true suppressed one,
and called it a fix. Ruling clause 4 exists so the next one does not.
