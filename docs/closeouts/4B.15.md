3. ITEM 0 -- THE DISCREPANCY, SETTLED
================================================================================

4B.14's close-out is CORRECT. The live synthesis answer was wrong, and the
fault IS date resolution.

READ FROM THE PERSISTED DOCUMENT:

  PAINT-01 calendar, Tue 2026-01-13:  07:00-19:00 REGULAR (open, no closure)
  PAINT-01 work on 2026-01-13:        NONE. Zero chunks overlap that day.
  The only machine working Jan 13:    CUT-01, ORD-000013 op10, 07:00-14:06

WHERE "07:00 to 11:24" CAME FROM. It is real, contiguous PAINT-01 occupancy --
on Tuesday 2026-01-06, the OTHER Tuesday in the window:

  07:00-09:17  ORD-000038 op30   (137 min)
  09:17-10:31  ORD-000002 op20   ( 74 min)
  10:31-11:24  ORD-000012 op30   ( 53 min)

Three back-to-back operations, ending at exactly 11:24. A TRUE FACT ABOUT THE
WRONG DAY.

THE FAULT, NAMED. Nothing told the model what day it was. Neither governed
prompt carried a reference date, a horizon, or any weekday mapping, and the
horizon spans 2026-01-05 to 2026-02-09 -- five Tuesdays. Asked about "Tuesday"
the model bound it to the first one in the tool result. The blocker analysis
reasoned correctly about Jan 13 in the same session because it COMPUTES with
dates and never reads a weekday off a row.

IT DOES BEAR ON THE SENTENCE THE PRODUCT IS MOST PROUD OF -- but it does not
weaken it. The 4B.14 chain re-verified end to end from the snapshot:

  op20 splittable = false, min_chunk = none    (observed, IDS: splittable)
  setup 20m + run 6h51m                        = 431 working minutes
  op10 ends Tue Jan 13 14:06 on CUT-01         (precedence)
  PAINT-01 closes 19:00                        -> 294 minutes remain
  294 < 431                                    -> cannot fit Tuesday
  Wed Jan 14 = planned_maintenance closure     -> next opening is Thu Jan 15
  op20 actually runs Thu Jan 15 07:00-14:11    = 431 minutes exactly

FIXED: `question_parser.render_calendar` puts the reference date (with its
weekday) and the horizon span into the shared context block, and synthesis
prompt rule 10 says a bare weekday is ambiguous, must be resolved or stated,
and must never be taken from whichever row appeared first. Prompt bumped to v3.

  A matched route could not be wrong. It can now: the check runs on the

5. CAN A PLANNER NOW ASK ANY DECLARED FIELD AND GET IT?
================================================================================

YES, WITH TWO STATED LIMITS.

WHAT WORKS. Verified live against the pinned world:
  splittable, min_chunk, setup_family, sequence, wip_status, run/setup duration,
  eligible machines (resolved to names, not "1 entry"), due, release/earliest
  start, quantity, commitment_class, customer, product, status, and on a
  resource: capacity, cost_rate, capabilities, resource_type, calendar.
Plus any field with no authored alias, by its own name -- the vocabulary comes
from the entity models, so it does not need extending when an entity does.
Every value carries its provenance class and, where one exists, the submission
column and the docs/06 section. An UNDECLARED field says "not declared" and
never "none" or "0" -- those are different facts.

LIMIT 1 -- THE FIELD MUST BE ON AN ENTITY THE RUN PERSISTED. Contract-1.12
document fields (`AssignmentBlock.splittable`) are NOT the source; the canonical
snapshot is, which is why this works on a world minted before 4B.14 landed 1.12.
A field that exists only on the document and not on an entity is not reachable
this way.

LIMIT 2 -- THE SECOND TIER STILL CANNOT READ A FIELD. Measured in the tier
bench: Sonnet's one failure was `hop-field-source`, where the parse chose
synthesis over attribute-lookup and synthesis answered, honestly and at length,
that per-operation submission data "is not something the placement, cost, or
lateness tools expose". It is right -- the toolbox has no attribute reader. When
the parse sends a field question to the second tier, the tier cannot answer it.
NAMED, NOT FIXED (see section 6).
