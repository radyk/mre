## 1. ITEM 1 -- THE VERDICT: (c) CALLED CONDITIONALLY

**The chain was never broken and nothing was swallowed. Beat two was guarded by
a condition, and the condition was false on the dense board.**

The site, verbatim, at `src/cockpit/src/drag/controller.js` (pre-fix line 465):

```js
        if (!ghost.feasible) {
          // beat one already proves it impossible -- snap back (no beat two).
          markCarryGhost(false);
          return returnHome(ghost.message || "this placement isn't possible");
        }
        return _beatTwo(pin, t, t0, ghost);
```

`ghost.feasible` is computed server-side in `src/mre/modules/sandbox.py`:

```python
    feasible = solve_result.status in ("OPTIMAL", "FEASIBLE")
```

**So `feasible == False` fuses two different things.** INFEASIBLE means the
solver PROVED no placement exists -- a fact about the plant. UNKNOWN means the
check ran out of its 2-second budget before deciding -- a fact about us. Both
landed in the same branch, both were spoken with the same sentence
(`"this placement isn't possible here"`, also authored server-side for both),
and both skipped the priced beat.

On the dense board beat one returns UNKNOWN. So: one request, a card that was
then HIDDEN by `returnHome`'s default (`keepCard` defaults to false), and a bar
snapping home. Exactly the founder's trace.

## 3. ITEM 5(b) -- UNKNOWN IS NOT IMPOSSIBLE (the third instance of a ruled species)

`CostProof` gained a fourth state (`unreadable`, 4B.18) so a fact about our
STORAGE could not be spoken as a fact about the plant. `partitions()` went
tri-state (4B.21) so an unprovable split could not be reported as a proven one.
Here the same fusion sat on a BOOLEAN.

`FeasibilityGhost` now carries `verdict`, and `classify_feasibility(status)` is
the single pure mapping:

- `possible` -- OPTIMAL / FEASIBLE. A placement exists.
- `impossible` -- INFEASIBLE. Proven that none does.
- `undetermined` -- UNKNOWN, **and anything unrecognised**. The check did not
  finish. The fail-safe direction is deliberate: "I don't know" is always a true
  thing to say about our own process, while "impossible" is a claim about the
  plant.

`feasible` keeps its exact meaning (PROVEN possible) and is now **never
sufficient on its own to author a sentence about the plant** -- asserted on both
sides of the wire (the client's `feasibilityVerdict()` falls back to `status`,
not to the boolean, when an older server sends no `verdict`).

The authored copy is part of the ruling and is tested as such: the UNDETERMINED
sentence must name its budget and must not contain "impossible" / "isn't
possible"; the IMPOSSIBLE sentence must say the opposite and must not mention a
budget.

**Both `possible` and `undetermined` now proceed to beat two.** Only a PROVEN
refusal stops the chain.

## 4. ITEM 3 -- A REFUSAL AND A FAILURE ARE DIFFERENT THINGS

The defect was invisible because the only exit from a beat that produced no card
was `returnHome` with the card hidden. One animation stood for a refusal, a
timeout, a crash, a dropped connection and a closed calendar.

Four exits now, none silent:

| what happened | who it is about | card | affordance |
| --- | --- | --- | --- |
| Tier-0 says no (closed calendar, ineligible) | the plant | `Can't go here`, rejected register | Close |
| beat one PROVES infeasible | the plant | `Can't go here`, rejected register | Close |
| a beat could not be run at all | **us** | `Couldn't price this`, judgment register | **Try again** |
| beat two ran out of budget (`no_verdict`) | **us** | `Couldn't price this`, judgment register | **Try again** |

The register split is deliberate: a failure does NOT wear the rejected colour,
because that colour means "the plan refused you" and nothing refused anything.

Two more things this fixed on the way:

- **The pending card was lying by construction.** `showPricing` rendered
  *"this is possible here -- pricing it now"* BEFORE the request was sent. On
  every drop it asserted an answer nobody had yet, and on the dense board the
  answer four seconds later was the opposite. It now says
  *"seeing whether this can go here at all"*.
- **A Tier-0 refusal used to lose its reason at the release.** `returnHome`
  hides `reasonTip` as its first act, so the "closed here, or won't fit before
  close" a planner saw mid-drag vanished at the exact moment they let go. It now
  rides the same card.

**No raw transport string reaches a planner surface.** `failureCause(e)` maps to
an authored sentence by class (5xx / 4xx / no response); the raw text lives on
`drag.state().failure.technical` and in `console.warn`, for whoever is debugging,
which is not the planner. Asserted negatively in the guard: the card must not
match `/Failed to fetch|HTTP \d{3}|\/schedules\//`.

## 6. ITEM 4 -- THE POLL CANNOT DISCARD A LIVE PROPOSAL

**Mechanism chosen: SUPPRESS.** Stated with its alternatives, because the choice
is the deliverable here.

A dropped bar awaiting its verdict, and the delta card that follows it, are
OPTIMISTIC CLIENT STATE: they exist nowhere in the persisted document.

- **Reconcile** needs two versions of a placement and there is only one. There is
  nothing in the document to reconcile the proposal against.
- **Hold above** means re-projecting absolutely-positioned overlay geometry after
  every reflow -- machinery for a state that lasts seconds.
- **Suppress** is exact, and costs nothing: the watch exists so a planner is not
  left on a stale board, which is not urgent inside a gesture.

`installFreshnessWatch` takes a `proposalLive` predicate and defers the WHOLE
check while one is up -- **before the request and again after it**, because a
drop can land while the listing is in flight and the decision must be made
against the state that exists now.

This is deliberately **narrower than `hasUncommittedState`**. A panel selection
is uncommitted state too, and 4.4 CU2 rules that it gets the BANNER; that is
unchanged, and its test still passes. Only a live sandbox proposal defers the
check entirely -- because even the banner is PREPENDED into `#app`, which
shortens the board host and moves the rows the proposal's overlay is pinned to.

`proposalLive` reads BOTH the drag phase and `cardOpen`, because a refusal /
failure / no-verdict card **outlives its gesture** (phase returns to idle while
the card stays). `cardOpen` is read from the DOM so it cannot drift from what the
planner is looking at.

**Deferred, never dropped.** The guard asserts the poll ran and held off
(`freshnessDeferrals()` incremented -- so a watch that was simply never called
would fail), that the URL did not change, that no banner was inserted, that the
card survived -- and then that dismissing the card and re-running the SAME check
offers the newer board.

4B.5's sticky-dismissal (`dismissedIds`), one-offer-per-id idempotence
(`offered`) and `preserveViewport` are untouched and still on the same path.

## 7. WHAT WAS TEMPTING AND LEFT

- **Making beat one fast.** The measurement points straight at a model cache and
  the cache is easy to write badly. Named and priced in 5(a); not attempted.
- **Making beat two deterministic.** `sandbox_pin_resolve` passes
  `time_limit_seconds` with **no `deterministic_time`**, so beat two is a
  wall-clock-bounded solve at `workers=1` -- which this repo's own hard rule says
  is not reproducible. It is why the identical pin returned `feasible_unproven`
  for 4B.22a and `no_verdict` for this session's first probe. **REPORTED, NOT
  FIXED:** giving beat two a deterministic budget changes what every existing
  gesture returns, and that is a ruling.
- **Retiring `feasible` from `FeasibilityGhost`.** It is now never sufficient to
  author a sentence, which makes it nearly vestigial -- but it is on the wire and
  read by the fixture server and older clients. Removing it is a contract-shaped
  change and was out of scope.

## 8. REPORTED, NOT FIXED -- new findings

**(a) R-DP9's NO-OP TOLERANCE SCALES WITH THE ZOOM, AND SWALLOWS REAL MOVES.**
`isNoOpDrop` computes `tolMin = feel.snap.grid_px * geometry.pxToMinutes(1)`. On
the dense board's default ~30-day view one pixel is about half an hour, so the
tolerance is **~240 minutes** -- and the 4B.22a collision gesture is **236
minutes**. Dropped at the default zoom it is treated as "already here": no card,
no sandbox call, phase back to idle, a cue that says the bar is where it was.
This cost the first three gestures of section 5 an entire run before it was
found, and it is indistinguishable, to a planner, from the defect this session
fixed. Every measurement above therefore zooms the board to the drop first, the
way a planner would. **The fix is probably a tolerance in MINUTES with a pixel
floor, not a pixel tolerance converted to minutes** -- but R-DP9 is a ruling and
its tolerance is a feel token, so this is a call, not a repair.

**(b) THE `feel.sandbox.budget_s` COMMENT WAS WRONG ABOUT WHAT IT DID.** It read
"The server budget is authoritative; this only paces the countdown animation."
The client SENDS this value as `budget_s` and the API honours it, falling back to
its own token only when the field is absent. This number is the real budget of
every drag. Comment corrected in the same commit; naming it here because the
15s-is-too-small finding was hiding behind a comment saying the number did not
matter.

**(c) A PRE-EXISTING RED TEST AT HEAD, NOT MINE.**
`cockpit.spec.mjs:111` ("deictic -- 'Why is this here?'") expects the resolved
question `"why is ORD-000012 on F001-RES001?"` and gets
`"why is ORD-000012 placed where it is on F001-RES001?"`. **Verified red at HEAD
with this session's changes stashed**, both themes. It is 4B.21's `why-on-machine`
rewording arriving without its browser assertion. Left alone: correcting it means
deciding which wording is right, which is a vocabulary call.

**(d) THE `planner.spec.mjs` DUE-MARKER FLAKE FIRED AGAIN**, dark theme, in a
full-suite run; passes in isolation (verified). Second member of the standing
parallel-load screenshot-flake class named in CLAUDE.md. Unchanged.

**(e) BEAT TWO's `no_verdict` NOW HAS A "Try again" BUTTON THAT RE-RUNS THE SAME
PIN AT THE SAME BUDGET.** Honest -- the budget is a wall-clock limit and a second
attempt genuinely can differ (see section 7) -- but it does not offer the one
thing that would reliably help, which is *more time*. A "try harder" affordance
that raises the budget for one gesture is the obvious next move and was not built.
