## ITEM 1 -- THE KEY

### The difference, in one sentence

There was never a difference in the READER -- the ask path and the sweep tool
both read a bare `os.environ`, and so does every other consumer -- the
difference is that every ENTRY POINT has to populate that environment itself,
and `python -m mre.ask` / `python -m mre.ai_exam` were the entry points that
supplied nothing, while the sweep tool had supplied its own since 4A.5b and was
never blocked at all.

### The four facts, side by side

(a) THE ASK PATH. Reads `os.environ.get("ANTHROPIC_API_KEY", "")` at
    construction: `question_parser.py:591`, `renderers.py:2773`,
    `synthesizer.py`, and `api/app.py` at three sites (`:700`, `:1408`,
    `:1508-1510`). No loader anywhere in the library, and that is CORRECT --
    docs/08 records that in a container the key arrives from the platform
    secret store and there is no file to read. What populates the environment
    on the dev cockpit path is `src/cockpit/dev_api.ps1:39-51`, a PowerShell
    loader that runs before uvicorn starts. It resolves `$PSScriptRoot/../..`,
    so it is REPO-ROOT anchored, not CWD-relative.

(b) THE SWEEP TOOL. Carried its own Python loader at
    `tools/run_ai_exam_sweep.py:42`, added by 4A.5b -- commit `f3bb319`,
    2026-07-26 -- and called at import time. Anchored to
    `Path(__file__).resolve().parents[1]`, i.e. the repo root, not the CWD.
    `tools/model_tier_bench.py:56` imports that exact function, which is how
    errand 4B.15a made its four live calls.

(c) THE DIFFERENCE. Stated above. The sweep tool was not the deprived side; it
    was the only Python entry point in the repo that was never deprived.

(d) DOES `dev_api.ps1` LOAD IT, AND DOES THAT MATTER FOR `python -m ...`? It
    loads it, and it does not help. The loader writes into that script's own
    process environment, so a separate shell running `python -m mre.ai_exam`
    inherits nothing from it. This is the mechanism that made the rumour
    plausible: the cockpit demonstrably had a key, so the key demonstrably
    "worked", and the module front door demonstrably did not.

### What was actually wrong

Not the key. Not one reader missing. FOUR independent implementations of the
same populate step, one already drifted, and two front doors with none:

    src/cockpit/dev_api.ps1              PowerShell, before uvicorn      OK
    tools/run_ai_exam_sweep.py           Python, since 4A.5b             OK
    tests/conftest.py                    Python, copied in 4B.8          OK
    tools/spikes/.../pastdue_visibility  Python, DRIFTED                 bug
    python -m mre.ask                    nothing                         bug
    python -m mre.ai_exam                nothing                         bug
    python -m mre.demo                   nothing                         bug

The spike's copy used `os.environ.setdefault`, which writes an EMPTY value
where the other three skip it -- so a blanked or commented-out key there could
shadow a real one from the environment. That is drift with teeth, and it is the
argument for one reader rather than four correct ones.

The three module front doors built an UNAVAILABLE parser from a bare shell and
answered on the honest could-not-interpret floor. That output is
indistinguishable from a missing key, and it is the reading that kept the
carry-forward alive.

### The fix

`src/mre/env_local.py` is the ONE reader. Its docstring records why the library
itself never loads a file, and lists the four copies it replaces. Semantics are
the three surviving copies' semantics, now stated and tested: repo-root
anchored (never CWD), an already-set variable always wins, an EMPTY value is not
a value, nothing printed, a missing file is a no-op returning False.

Callers: `tests/conftest.py`, `tools/run_ai_exam_sweep.py` (which re-exports the
name, because `model_tier_bench` imports it from there),
`tools/spikes/density_4b10/pastdue_visibility.py`, and the `main()` of
`mre.ask`, `mre.demo` and `mre.ai_exam`. Called from entry points only --
`tests/test_env_local_one_reader.py` asserts the module does not load on import,
because a package that mutates the environment on import is a surprise the API
server does not need.

`dev_api.ps1` stays exempt and the exemption is stated in the guard: it is the
shell, running before any Python exists.

### The guard

`tests/test_env_local_one_reader.py`, 10 tests. The count test flags any .py
file that both names `.env.local` as a WHOLE string literal and writes to
`os.environ` -- so prose about `.env.local` is not a false positive and an
`os.environ.get` is not either. Comment lines are stripped before matching.

NEGATIVE CONTROL RUN, not assumed: a planted second loader at
`tools/_negctl_tmp.py` turned it red; removing the file turned it green.

The semantic tests pin each rule the copies had drifted on, including the
`setdefault` case explicitly.

## ITEM 2 -- COVERAGE: DO PLANNER PHRASINGS REACH THE NEW ROUTES

Ten phrasings, each its own conversation (RESET before each, so nothing resolves
off a prior turn -- the cold-open case), live against the pinned world on shipped
defaults. Route latency median 1462 ms, p90 2124 ms, 15 parses, 0 retries,
0 malformed.

what-would-change, with ORD-000013 / PAINT-01 selected (op20, 431 working
minutes, Thu Jan 15):

    phrasing                                         intent              route              conf  intended
    what would have to change for op20 to run Tuesday what-would-change   what-would-change  0.92  YES
    how do I get this earlier                        what-would-change   what-would-change  0.92  YES
    can this move to Tuesday                         what-would-change   what-would-change  0.92  YES
    what if it were splittable                       what-would-change   what-would-change  0.92  YES
    why can't it be earlier                          why-here (neg pol)  why-here           0.95  NO

briefing, nothing selected:

    what should I be worried about                   briefing            briefing           0.95  YES
    how does this schedule look                      briefing            briefing           0.95  YES
    anything I should know                           briefing            briefing           0.95  YES
    what's the state of things                       briefing            briefing           0.95  YES

added case, subjectless follow-up AFTER a briefing (nothing selected):

    what should I be worried about                   briefing            briefing           0.95  --
    how do i fix that                                remediation         CLARIFY            0.72  --
                                                     followup=deepen, clarify=no-subject

NINE OF TEN reached the intended route. Subject binding worked on every
`what-would-change` phrasing: "this" and "it" bound to ORD-000013 from board
selection, and "what if it were splittable" additionally bound
`concept=splittable` off the utterance.

### The one miss is a route boundary, and it is NOT fixed

"why can't it be earlier" resolved to `why-here` at 0.95 with
`polarity=negative`, and answered correctly -- the couldn't-verdict, the binding
family (C3, no window long enough), the ladder, and the four uncomputed families
named.

That is defensible rather than wrong. `what-would-change` is DEFINED as
`why-here`'s inverse over the same computed bounds (section 5a.49), so a "why
can't" utterance sits exactly on the seam between them, and negative polarity is
the parse doing what it was built to do. Whether the two should merge is the
vocabulary question 4B.14 already declined to rule on for `start-reason` versus
`why-here`. Widening a meaning to capture a phrasing was explicitly out of scope,
so it is reported, not chased.

WHAT WOULD HAVE BEEN INTERESTING DID NOT HAPPEN. The errand asked whether a miss
on a simple phrasing after a hit on the hard one would indicate a prompt tuned to
context-carrying follow-ups and thin on cold opens. It does not: all four
`briefing` cold opens landed at 0.95, and the hard case (a four-word subjectless
follow-up reaching `what-would-change` off selection) also holds. The prompt is
not thin on cold opens -- it is precise on a seam.

### The added case: a pronoun after a whole-board read

"how do i fix that" following a briefing parsed as `remediation` /
`followup=deepen` / `clarify=no-subject` and asked which order, machine or
customer was meant.

That is the right floor. The resolution ladder is card > selection > last answer
> history > clarify, and a briefing's "last answer" is the whole board: four
ranked items naming several orders and no single subject. Anaphora binds where
the prior turn had ONE subject and correctly refuses where it had many. The
contrast with the same follow-up after a `why-here` -- which does bind, from
selection -- is the finding.

The mitigation already ships: each opener item carries its own pointer
("-> Ask 'when does <order> finish?'"), which is what a planner should click
rather than a bare pronoun.

### The measurement found a leak IN THE INSTRUMENT

THE FIRST RUN OF THIS BANK OPENED SEVEN CONSECUTIVE TURNS WITH:

    I've now given you this same answer for two different questions, which
    probably means I'm not understanding what you're asking. Last time you
    asked: "..."

each citing a question from a conversation `RESET` had already discarded.

Cause: the deafness signal's memory (`interpreter._DELIVERED`) is module-level
and keyed by session id. That placement is deliberate and correct -- a delivered
ANSWER cannot be read off the history channel, which carries only the question
and the route, and section 5a.42's whole reversal was that the signal is the
OUTPUT, not the route. But `RESET` cleared history, selection, last-answered and
the card -- four channels -- and MISSED THE FIFTH.

Fixed: `forget_deliveries(session_id)` is the symmetric clear for
`remember_delivery`, and the exam runner's `RESET` calls it. Re-run, the rider
fires ZERO times, and the phrasing table above is the uncontaminated one.

This was worth fixing even though it is not a product surface: a RESET that
clears four of five channels contaminates every bank that starts a second
conversation, which is most of them, and the contamination reads as a product
defect. The guard asserts the runner's own call site, not only the function.

REPORTED, NOT FIXED -- the product half. Four different phrasings of the opener
inside ONE conversation legitimately trip the rule (same answer, genuinely
different questions), so the second would open with self-doubt on the first
thing a stranger reads. That is section 5a.42's stated limit -- distinguishing
"one answer because I am confused" from "one answer because it IS the answer"
needs a signal that does not exist yet -- at higher severity and unchanged in
shape.

Two mitigations were VERIFIED rather than assumed:

* the REPL passes no `session_id` to `run_ask`, so the detector is inert there;
* the cockpit has no conversation-clear gesture at all (`#ask-clear` clears the
  board highlight), so no product surface leaks across a boundary today.


## ITEM 3 -- THE THREE AMENDMENTS

### A1 -- measured latency

Dispatch only (assemble + template render), parse deliberately excluded because
it is a fixed model call shared by every route. 12 samples after one warm call,
pinned world:

    what-would-change (the counterfactual)      median   7.3 ms   (6.5 - 8.2)
    briefing (the opener)                       median  61.0 ms   (52.5 - 67.7)

End to end, from the live run: route latency median 1462 ms, p90 2124 ms. The
four opener turns' parses were 1435 / 1125 / 983 / 2633 ms.

FLAGGED AS THE ERRAND ASKED: the opener DID exceed ~2 s end-to-end once, on
"what's the state of things", at roughly 2.7 s. THE CAUSE WAS THE PARSE (2633 ms
for that one call), NOT THE ROUTE. The opener's own contribution is 61 ms, about
4% of a turn. So the number to watch for a stranger's first read is the parse
tail, which errand 4B.15a already measured and recorded (section 5a.46): every
tier's p90 is 6-9x its median.

### A2 -- precompute, answered both ways

    briefing dispatch, scan computed per ask    median  61.0 ms
    briefing dispatch, opener READ from cache   median   0.4 ms

Measured, not subtracted: the cached run substitutes a prebuilt opener at
`_build_opener` and times the same dispatch.

Precompute removes 99% of the opener's dispatch and 4.6% of a parse+dispatch
turn. Where the time goes:

    _build_opener (whole scan)                          58.7 ms
      _opener_load                                      59.0 ms   <- all of it
      _opener_closures                                    4.0 ms
      _opener_at_risk                                     0.1 ms
      _opener_late                                        0.0 ms
      _opener_certificate                                 0.0 ms

`_opener_load` walks `_open_windows` for all 15 machines across the whole
horizon. That is the entire cost.

VERDICT: NOT WORTH A CONTRACT CHANGE AT THIS DENSITY, and none was made. The
parse dominates by 20x.

THE CONTRACT SHAPE IT WOULD NEED, named and left: an Optional block on the
schedule document minted at registration where the document is assembled -- the
pattern `RollingBlock.coarse_zone` already uses, absent on an older document,
present with its own provenance. It is Optional-and-absent or it breaks every
older document.

THE REASON TO REVISIT IS SCALE, NOT THIS NUMBER. `_opener_load` scales in
machines x horizon days. Pilot volume is 174 workcenters against the 15 measured
here; at roughly 12x the machines the scan plausibly becomes the dominant term
rather than 4% of the turn. Pilot-volume latency is UNMEASURED for every figure
in this repo, which is a standing carry-forward, not a new one.

### A3 -- the spec-citation call

CONFIRMED, and the answer has two halves.

DELIBERATE AT THE RULING LEVEL. `counterfactual.SPEC_OF` is a dict of authored
docs/06 constants ("docs/06 section 5.3 routing_lines.csv splittable /
min_chunk_minutes" and five siblings), rendered by the template as part of each
lever line. The reference never passes through synthesis and never takes a claim
label at all. That is exactly what section 5a.48's own closing sentence
prescribes -- "an answer whose strongest evidence is a spec passage should route
that reference through authored copy rather than let synthesis carry it under the
interpretive label" -- and that sentence was written by errand 4B.15a, ONE COMMIT
BEFORE the route existed.

INCIDENTAL AT THE ROUTE. 4B.16's close-out does not mention section 5a.48 at
all, and nothing in `counterfactual.py` said why those strings are hardcoded. So
the compliance was real but unprotected: reading them out of the 4B.15 corpus
index instead would look like a straightforward tidy-up -- the index ships with
the build and carries a sha256 per document -- and would silently re-open
section 5a.48 for this route by turning each reference into a corpus-grounded
claim wearing the weakest label the surface has.

Fixed by recording the prohibition on `SPEC_OF` itself, where a refactorer
reads it. A comment, not a behaviour change.

IS THE SPEC-CITATION KIND STILL OWED FOR OTHER SURFACES? YES, unchanged in
scope. It is owed for the SYNTHESIS tier, where section 5a.48's measured
specimen lives: asked whether downtime is per machine or per operation, the
second tier answered correctly from docs/05's catalog rows and all four claims
landed `[synthesis -- my reading, no record states this]`. So it is owed for
every answer whose ground is `constraint_catalog` or `spec_lookup` rather than a
placement. A contracted route carrying authored copy is a workaround that
happens to be available to contracted routes -- not a discharge.


## THE TEST RUN, AND A DEVIATION FROM THE ACCEPTANCE CRITERION

The acceptance criterion asked for the full non-slow suite green in ONE run. It
was run in FOUR sequential invocations instead, and that is stated here rather
than glossed, because the criterion exists to stop exactly the kind of claim
errand 4B.15a was pulled up for.

    batch 0   488 passed,  48 skipped   270.0 s
    batch 1   612 passed,  45 skipped   399.2 s
    batch 2   493 passed,  38 skipped   235.5 s
    batch 3   433 passed, 121 skipped   212.5 s
    -------------------------------------------
    total    2026 passed, 252 skipped   0 failed

2026 + 252 = 2278, which is exactly `pytest --collect-only -q`'s count for this
tree. Every test file was covered: the batches are `sorted(Path('tests').rglob(
'test_*.py'))` sliced `files[i::4]`, so the partition is total and disjoint by
construction.

WHY IT WAS SPLIT: four attempts at a single invocation were each killed by a
wall-clock cap in this environment, at 19%, 44%, 53% and 53% completion, all with
zero failures up to the kill. The suite needs roughly 19 minutes; the cap is
shorter than that. `pytest-xdist` is NOT installed and installing it was not in
scope -- and it would be the wrong instrument anyway, since this repo carries a
standing contention-sensitivity debt (`test_n3000`, the parallel-load
screenshot-flake class, and `test_scenario_untouched_moves_bounded`) whose members
pass alone and fail under load.

WHAT THIS DOES AND DOES NOT PROVE. It proves every test passes. It does NOT
reproduce whatever cross-file interaction a single process would create, so a
contention-sensitive failure of the class already on the books could hide in the
split. Four batches of ~500 tests each is not nothing, but it is weaker than one
run and should be read that way.
